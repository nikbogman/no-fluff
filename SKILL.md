# No-Fluff

Make documentation and comments say more with less. The goal is not
documentation coverage — it's information density. Every sentence should earn
its place.

This is a deletion tool. Read "Never edit" and "Preconditions" before touching
anything.

## Reference files

Read the relevant reference before editing:

- **`references/comments.md`** — code comments, inline comments, docstrings.
  Litmus tests, what's safe to delete, worked examples. Read when touching
  source files.
- **`references/docs.md`** — Markdown docs and READMEs. Ownership hierarchy,
  writing style, format conversions, README scope, validation. Read when
  touching `.md` files.

Read both when a task spans code and docs — duplication between a docstring
and a README is only visible from both sides.

## Preconditions

Before any multi-file or bulk run:
- **Working tree must be clean.** Check `git status`. If there are uncommitted
  changes, say so and let the user commit or stash first — this skill deletes
  text and the diff is the only undo.
- **Not in a detached or mid-rebase state.**

If the repo isn't under version control, warn the user before a bulk run and
prefer the review path over direct edits.

## Never edit

Skip entirely — do not trim, reword, or reformat:

- **Directive comments.** These are code, not documentation. Deleting them
  changes build, lint, type-check, or runtime behavior:
  `// eslint-disable-next-line`, `# noqa`, `# type: ignore`, `# pragma: no cover`,
  `//go:embed`, `/** @jsx h */`, `# fmt: off`, `#!/usr/bin/env ...`,
  `# -*- coding: utf-8 -*-`, `@ts-expect-error`, `// prettier-ignore`,
  `// nolint`, `<!-- prettier-ignore -->`, and any comment a tool parses.
  If a comment might be read by a tool rather than a human, leave it.
- **Generated files.** Anything with a "generated by X — do not edit" header,
  plus auto-generated API docs, OpenAPI/protobuf/GraphQL client stubs, and
  tool-managed CHANGELOGs. Editing them produces a diff the next build reverts.
- **Vendored and dependency directories.** `node_modules/`, `vendor/`,
  `third_party/`, `.venv/`, anything gitignored.
- **Migration files.** Historical by nature; their comments record intent at a
  point in time.
- **Doctests and executable examples in docstrings** (Python `>>>` blocks,
  Rust doc examples). These are tests. See `references/comments.md`.

When in doubt about whether something is generated, check for a header, a
`.gitattributes` `linguist-generated` marker, or an obvious build step that
produces it — then skip it and mention it in the summary.

## When this applies

**Active / invoked mode** (`/nofluff`, "simplify documentation", "clean up
these comments"):
1. If the user named specific files, work on those only.
2. If no files were named and you're in an interactive session, ask which
   files or directories to target before doing a bulk pass. Don't silently
   rewrite the whole repo's docs on a vague request — that's a large,
   disruptive diff nobody asked for.
3. If no files were named and no interactive follow-up is possible (fully
   autonomous run), apply to all documentation in the repo.

**Passive / standing-behavior mode** (when a project's AGENT.md or CLAUDE.md
instructs the agent to write fluff-free): apply these rules in real time to
documentation, comments, and docstrings the agent itself writes or edits.
Write it clean the first time rather than writing verbose and revisiting.
The review gate below does **not** apply here — it governs edits to
pre-existing content, not the agent's own fresh output.

Standing behavior belongs in AGENT.md rather than in this skill's trigger
conditions — always-in-context rules are more reliable than skill triggering
for something that should apply continuously. If the user wants this, point
them at the "Standing behavior" section of `README.md`.

## Edit vs. review

- **Single file or user-specified target(s):** edit directly.
- **Whole-repo or bulk run:** don't mass-edit silently. Summarize first and
  confirm before applying (or open a diff/PR, depending on the environment).

The summary should list, per file: what was cut and roughly how much, anything
moved to another document, anything that couldn't be verified against the code,
and anything skipped under "Never edit". Keep it scannable — a table, not prose.

## What counts as fluff

Cut:
- **Restating the obvious** — `i++ // increment i`, `// Constructor` above a constructor.
- **Verbosity** — multiple sentences where one clear sentence covers it.
- **Duplication** — the same explanation in a docstring, a comment, and the README.
- **Hedging and filler** — "It should be noted that...", "Basically...", "Simply".
- **Narration** — describing *what* self-explanatory code does. Keep *why*, cut *what*.
- **Padding** — boilerplate intros, "In this section we will discuss...".
- **Stale content** — descriptions, commands, or config that no longer match the code.

Keep:
- **Why, not what** — rationale for non-obvious decisions, tradeoffs, gotchas,
  workarounds for external constraints.
- **Contracts** — units, valid ranges, side effects, error conditions, anything
  a caller can't infer from the signature.
- **Examples** — only when the usage pattern is genuinely non-obvious.

Add only where critically missing: a public symbol with *no* docs whose purpose
isn't obvious from its name and signature gets one to three lines, no more.
Coverage is not the goal. See `references/comments.md`.

## Priority order

For any piece of text, work through this order and stop at the first that applies:

1. **Delete** — provides no meaningful value. Don't rewrite it shorter, remove it.
2. **Compress** — matters, but takes more words than needed.
3. **Convert** — clearer as a bullet list, table, or command block.
4. **Move / reference** — belongs in another doc; relocate it or link to it.
5. **Keep as-is** — already necessary and concise.

Don't rewrite by default. Deletion is usually the biggest improvement available.

## Check the history before deleting

The odd-looking comment is often the important one — it was added at 2am after
an incident. Before deleting a comment that looks redundant *but is oddly
specific* (a magic number, a named vendor, a version, a date, a defensive
check):

```bash
git log -S "<distinctive phrase>" --oneline -- <file>
git blame -L <line>,<line> -- <file>
```

If it arrived with a bug fix, an incident response, or a revert, it stays —
that specificity is the information. If it arrived with the original feature
commit and says nothing the code doesn't, it goes.

Skip this check for clearly generic comments (`// loop through users`); it's
for the ones that made you pause.

## Process

1. **Check preconditions.** Clean tree, scope agreed, exclusions identified.
2. **Inspect structure.** Map the repo's documentation: READMEs, architecture
   or design docs, domain/glossary docs, service-level docs, comment blocks.
3. **Locate targets.** List every file actually in scope, minus "Never edit".
4. **Understand purpose.** Work out what each doc owns — infer from how the
   repo already organizes things; don't impose an external structure.
5. **Identify problems.** Duplication, verbosity, stale content, obvious
   comments, text that provides no value.
6. **Cut obvious comments.** See `references/comments.md`.
7. **Simplify verbose docs.** See `references/docs.md`. Preserve every
   technical fact — trim the words around it, never the information itself.
8. **Consolidate ownership.** Move or reference misplaced/duplicated
   information rather than repeating it.
9. **Validate against the codebase.** Referenced files exist, links resolve,
   commands and config names match reality. Don't invent information — if
   something can't be verified, leave it and flag it.
10. **Final pass.** Re-read as a developer new to the project. Anything still
    deletable without losing useful information? Delete it.

Match the surrounding style and format throughout — Markdown conventions,
docstring style — inferred from what's already there. Never switch styles as
part of a trimming pass.

## Constraints

This is a documentation and comment skill, not a refactoring skill:
- Never change application behavior.
- Don't redesign architecture or restructure code because you spot an opportunity.
- A small code change (renaming a variable, extracting a trivial helper) is
  acceptable **only** when it directly lets you delete a comment that was
  compensating for unclear code, and it must preserve behavior exactly.
- In direct-edit mode, actually edit the files — don't stop at a list of
  suggestions.

## Commit hygiene

Land documentation and comment changes in their own commit, separate from any
behavior change. This makes review trivial and revert cheap. If the working
tree already contains behavior changes, don't fold trimming into them — say so
and let the user decide.

Suggested message shape: `docs: trim <area>` or `chore(docs): remove redundant
comments in <module>`.

## When to stop

**A pass that finds nothing to cut is a successful pass.** Report that plainly
and change nothing.

Do not manufacture edits to justify the run. Rewording something that was
already fine is a regression: it costs review time, pollutes git blame, and
risks losing meaning. If the docs are clean, say "these are already concise —
no changes needed" and stop.

The work is done when every remaining sentence would be missed if deleted.

## Scope note (currently trim-everything)

Beyond the "Never edit" list, there's no per-comment exemption mechanism —
the same rules apply to license/legal headers and compliance-mandated text.
If this causes a problem (e.g. legally required wording gets reworded), flag
it to the user rather than assuming. An inline marker convention (e.g.
`// NOFLUFF-IGNORE`) or a configurable exemption list is a natural future
addition, not yet implemented.
