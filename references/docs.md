## Don't edit these

Skip and note in the summary:

- **Generated documentation** — API reference built from docstrings
  (Sphinx/TypeDoc/Javadoc output), OpenAPI or GraphQL schema docs, anything
  with a "generated by X — do not edit" header. Fix the source, not the output.
- **Tool-managed CHANGELOGs** — files maintained by release-please,
  semantic-release, changesets, or similar. Editing them breaks the tool.
- **Vendored docs** — anything under `node_modules/`, `vendor/`,
  `third_party/`, or gitignored paths.
- **Templates and boilerplate with required structure** — issue and PR
  templates, `CODE_OF_CONDUCT.md`, `LICENSE`, `SECURITY.md`. Their wording is
  often standardized or legally significant; verbosity there isn't a bug.
- **Markdown directives** — `<!-- prettier-ignore -->`,
  `<!-- markdownlint-disable -->`, front-matter fields consumed by a static
  site generator, and doc-site includes/snippet references.

Docs under `docs/` that feed a published site may have structural
requirements (sidebar ordering, required front-matter). Check for a site
config before restructuring headings or renaming files.

## Establishing ownership

Most repos with several docs already have an implicit hierarchy. Discover it
before editing — don't impose a structure the repo doesn't use.

A common shape:

| Document | Owns |
|---|---|
| Root `README.md` | Overview, setup, getting started, links onward |
| `architecture.md` / `design.md` | Components, boundaries, data flow, decisions |
| `context.md` / `glossary.md` | Domain vocabulary and concepts |
| `services/*/README.md` | That service's usage, config, and constraints |
| `CONTRIBUTING.md` | Workflow, conventions, review process |
| Code + comments | Implementation, and why it's that way |

Your repo may name these differently or not have them all. Infer ownership
from what exists.

**Once ownership is clear:**
- Each fact lives in exactly one authoritative place.
- Duplicated explanation → keep it in the owning doc, replace the copy with a link.
- Misplaced information → move it to the owning doc; don't leave a copy behind.
- If two docs disagree, the owning doc wins; fix or delete the other.
- If no doc clearly owns something, prefer the most specific one that does.

Documentation should form a connected hierarchy, not a set of overlapping
retellings.

## Writing style

Write like an experienced engineer explaining something to another experienced
engineer. Respect the reader's time.

- Short sentences. Short paragraphs.
- Bullets for lists, tables for structured information, command blocks for commands.
- Clear headings — but don't add headings to sections that don't need them.
- Direct language over formal or promotional phrasing.
- Procedures in the order they're performed.
- Required steps visually distinct from optional notes.
- Scannable top to bottom: a reader should find what they need without reading
  the whole file.

Avoid:
- Marketing or promotional tone.
- Long introductions before the useful content.
- Explaining well-known technologies from first principles.
- Project history that doesn't affect current work.
- Excessive heading depth (`####` and below is usually a sign of over-structuring).

## Phrases to cut on sight

| Cut | Use |
|---|---|
| "In order to" | "To" |
| "It is important to note that X" | "X" |
| "Note that X" | "X" |
| "As you can see" | *(delete)* |
| "Simply" / "Just" / "Obviously" / "Basically" | *(delete)* |
| "This section will explain..." | *(delete — the heading said it)* |
| "You will want to" / "You should probably" | Imperative: "Run", "Set" |
| "There is a function called `foo` which does X" | "`foo` does X" |
| "utilize" / "leverage" | "use" |
| "at this point in time" | "now" |

Structural cuts:
- A paragraph that could be a bullet → make it a bullet.
- A bullet that adds nothing → delete it.
- A table with one row → make it a sentence.
- A section with one sentence → fold it into the parent section.

## Format conversions

**Prose → table.** Several paragraphs each explaining one config variable:

> The `DATABASE_URL` variable is required and should be set to your database
> connection string. You may also optionally set `LOG_LEVEL`, which controls
> how much logging output is produced. If you don't set it, it will default
> to `info`.

becomes:

| Variable | Required | Description |
|---|---|---|
| `DATABASE_URL` | Yes | Database connection string |
| `LOG_LEVEL` | No | Defaults to `info` |

**Prose → commands.** "Before running the development server, you'll first
need to install the project's dependencies using npm..." becomes:

```bash
npm install
npm run dev
```

**Prose → bullets.** A paragraph listing four things in sequence with "and
also" and "in addition" becomes four bullets.

**Wall of text → linked sections.** If a doc has grown past what a reader can
scan, that's usually a sign content belongs in a different doc (see
[Establishing ownership](#establishing-ownership)) rather than a sign it needs
more headings.

## README scope

A root README should let someone answer, quickly:

1. What is this?
2. What does it do?
3. How do I set it up?
4. How do I run it?
5. How do I test it?
6. Where do I find more detail?

Keep it focused on getting a newcomer productive. It should **not** become:
- An architecture document → link to the architecture doc.
- A domain glossary → link to the context/glossary doc.
- A copy of each service's README → link to them.
- A project history or changelog → that's `CHANGELOG.md` and git.

Service/module READMEs answer the same shape of question, scoped to that
service: what it's responsible for, how to run/configure/test it, and any
service-specific constraints. They should not restate system architecture or
redefine domain terms.

## Validating against the codebase

Before finishing, verify the surviving documentation is actually true:

- Referenced files and paths exist.
- Links resolve (internal anchors included).
- Commands match the repo's actual scripts (`package.json`, `Makefile`, etc.).
- Config/env variable names match the code.
- Described behavior matches the implementation.
- Domain terms match the glossary's definitions.
- No two docs contradict each other.

Don't invent information. If something can't be verified from the repository,
leave it alone or flag it explicitly — never guess and write it as fact.

## Pass flow

1. Screen out everything in [Don't edit these](#dont-edit-these).
2. Map what documentation exists and what each file owns.
3. Read before editing. Duplication is only visible across files.
4. For each section, apply the priority order from SKILL.md: delete >
   compress > convert > move/reference > keep.
5. Consolidate: move misplaced content to its owning doc, replace copies with links.
6. Reorder for scannability — procedures in execution order, required before optional.
7. Validate against the codebase (above).
8. Final pass: re-read as someone who just joined the project. Anything still
   deletable without losing useful information? Delete it.

If a document is already concise, leave it alone and say so. Rewording
adequate prose is a regression — it costs review time and pollutes git blame
for no gain. Finding nothing to cut is a successful outcome.
